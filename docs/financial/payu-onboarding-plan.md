## Risk Assessment & Mitigation

### Payment Processing Risks

**Risk 1: Application Rejected**

**Causes:**
- Incomplete website (missing legal pages)
- Name mismatch (PAN vs bank account)
- Unclear business model
- Expired documents

**Mitigation:**
- Complete website checklist before applying
- Verify all names match exactly
- Clear tour business description
- Upload current, valid documents

**If Rejected:**
- PayU provides rejection reason
- Fix issues and reapply
- Typically 1-week delay

---

**Risk 2: Webhook Delivery Failures**

**Causes:**
- Server downtime during payment
- Firewall blocking PayU IPs
- Invalid webhook URL
- Slow server response (timeout)

**Mitigation:**
- Webhook endpoint monitoring (uptime checks)
- Whitelist PayU IP ranges
- Validate webhook signature (prevent spoofing)
- Return 200 OK quickly (<5 seconds)
- Process payment confirmation asynchronously

**Impact:**
- Customer pays but booking not confirmed
- Manual reconciliation needed
- Poor customer experience

**Recovery:**
- PayU retries webhook delivery (multiple attempts)
- Manual check: PayU dashboard vs database
- Implement fallback: Poll PayU order status API

---

**Risk 3: Chargebacks**

**Causes:**
- Customer disputes charge (claims service not provided)
- Fraudulent card (stolen card used)
- Customer confusion (doesn't recognize charge)

**Mitigation:**
- Clear billing descriptor (KrakowBites + Tour Date)
- Email confirmation immediately (proof of service)
- Take photos during tours (evidence)
- Respond to PayU chargeback requests within 7 days
- Provide documentation (booking, email, tour attendance)

**Typical Rate:**
- Tours: <1% chargeback rate (low-risk business)
- If >2%: PayU may investigate

**Cost:**
- Chargeback fee: ~50-100 PLN per case (even if won)
- Lost revenue if chargeback successful

---

**Risk 4: Refund Processing Failures**

**Causes:**
- Insufficient PayU merchant balance
- Original payment voided (too old)
- Bank account closed/frozen
- API error

**Mitigation:**
- Maintain positive balance in PayU account
- Process refunds within 60 days of payment (best practice)
- Monitor refund API responses (log errors)
- Manual fallback: Refund via PayU dashboard

**Impact:**
- Customer expects refund, doesn't receive
- Customer complaints, negative reviews
- Manual intervention required

---

**Risk 5: Low Initial Conversion Rate**

**Causes:**
- Checkout friction (too many steps)
- Lack of trust signals (new website)
- Payment failures (technical issues)
- High prices vs competitors

**Mitigation:**
- Simplify checkout (minimal fields)
- Display trust badges (PayU logo, SSL)
- Monitor payment success rate (>95% expected)
- A/B test pricing/checkout flow

**Measurement:**
- Track: Visitors → Booking Form → Payment → Confirmed
- Identify drop-off points
- Optimize highest-friction steps

## Settlement & Financial Reconciliation

### How PayU Settlements Work

**Payment Flow:**
1. Customer pays 200 PLN for tour on Monday
2. PayU processes payment, deducts 6 PLN commission (3%)
3. PayU holds net amount: 194 PLN
4. Settlement date: Wednesday (T+2)
5. PayU transfers 194 PLN to your bank account
6. Your bank shows deposit on Thursday morning

**Settlement Frequency:**
- Daily: Every business day (Mon-Fri)
- Weekly: Once per week (e.g., every Friday)
- Monthly: Once per month (for very low volume)

**Recommended:** Daily settlements for better cash flow

### Reconciliation Process

**Weekly Reconciliation:**

**Step 1: Export PayU Transactions**
- Log into PayU merchant dashboard
- Navigate to: Reports → Transactions
- Filter: Last 7 days
- Export to CSV/Excel

**Step 2: Check Bank Deposits**
- Log into business bank account
- Filter: Deposits from PayU
- Match amounts to PayU settlement reports

**Step 3: Verify Database Bookings**
- Query database: Bookings with status = 'confirmed'
- Sum total revenue for week
- Cross-check with PayU gross revenue

**Step 4: Identify Discrepancies**
- Missing webhooks: Payments in PayU but not in database
- Failed payments: Bookings in database but no PayU payment
- Refunds: Subtract from gross revenue

**Example Reconciliation:**

```
PayU Gross Revenue:     5,000 PLN (25 bookings)
Refunds Processed:       -400 PLN (2 cancellations)
Net PayU Revenue:       4,600 PLN

PayU Commission (3%):    -138 PLN
Net Settlement:         4,462 PLN

Bank Deposit Received:  4,462 PLN ✓

Database Bookings:      23 confirmed (5,000 PLN - 400 PLN refunds)
Match: ✓
```

**Red Flags:**
- Bank deposit < expected settlement (PayU error or bank delay)
- Database bookings ≠ PayU transactions (webhook failures)
- Missing transactions (fraud or technical issue)

## Technical Integration Overview

**Note:** Detailed technical implementation covered separately. This section covers business process only.

### Integration Types Available

**Option 1: Redirect (Simplest)**
- Customer clicks "Book Now"
- Redirected to PayU checkout page (PayU-hosted)
- PayU handles payment form, card data, 3D Secure
- Customer returns to your site after payment
- Webhook confirms payment status

**Pros:** Fastest to implement, PCI compliance handled by PayU
**Cons:** Customer leaves your website (potential drop-off)

**Option 2: Lightbox/Modal (Recommended)**
- Customer clicks "Book Now"
- PayU checkout opens in overlay/popup (stays on your site)
- PayU handles payment form within modal
- Modal closes after payment
- Webhook confirms payment status

**Pros:** Better UX (feels integrated), PCI compliance by PayU
**Cons:** Slightly more complex implementation

**Option 3: API Integration (Most Control)**
- Custom payment form on your website
- API calls to PayU for payment processing
- Full control over UX/UI
- Requires PCI compliance (if collecting card data)

**Pros:** Seamless UX, full customization
**Cons:** Complex, PCI compliance burden, not recommended for small business

**Decision for KrakowBites:** Option 2 (Lightbox) - best balance of UX and simplicity

### Webhook Configuration

**What Webhooks Do:**
- PayU sends HTTP POST to your server when payment status changes
- Notification types: Payment completed, payment failed, refund processed
- Your server updates booking status in database
- Sends confirmation email to customer

**Webhook Endpoint Requirements:**
- HTTPS only (SSL certificate required)
- Public URL (not localhost, not IP-restricted)
- Returns 200 OK within 5 seconds
- Validates PayU signature (security)

**Example Webhook URL:**
```
https://krakowbites.com/api/payu-webhook
```

**Configuration:**
- Set webhook URL in PayU merchant dashboard
- PayU sends test webhook (verify receipt)
- Production: Real payment notifications

**Solution:**

- Log into application portal to see status
- If >3 days with no update, email onboarding team

**Issue 2: Webhook Not Received**

**Cause:** Server issue, firewall, or PayU retry exhausted
**Solution:**
- Check server logs for incoming POST requests
- Verify webhook URL is publicly accessible (test with webhook.site)

**Cause:** Webhook processing error in your code

- Log all webhook payloads for debugging
- Check booking status in database

- Email customer with confirmation (manual intervention)

---

**Issue 4: Refund Rejected**

**Solution:**
- Check PayU merchant balance (must have funds for refund)
- Verify payment is <180 days old (typical refund window)
- Check API error message in logs
- Use PayU dashboard to process refund manually

---

**Issue 5: Customer Claims Non-Receipt**

**Cause:** Payment successful but confirmation email not sent
**Solution:**
- Check email service logs (SendGrid, etc.)
- Verify email not in customer's spam folder
- Resend confirmation email manually
- Provide booking reference via phone/WhatsApp
